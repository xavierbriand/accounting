## Keep

- **Probing beats changelog-reading, a fourth time, and extended to a semver-major this time.** `@cucumber/gherkin` bumped 41→42 — a semver-major, unlike the previous three occurrences' all-minor/patch "safe" sets — but the changelog read (i18n additions, a parser *relaxation* not a narrowing, a non-JS toolchain dependency-floor bump) plus a green full acceptance-test run made the "major" label a non-issue. Treating "major version number" as a prompt to actually read the changelog, not as an automatic escalation trigger, held up again.
- **The transient test flake was correctly not treated as a regression.** The very first baseline `npm test` run (before any dependency change) showed 2 failures in `tests/integration/cli/symlink-dbpath-refuse.test.ts`. Rather than either ignoring it or wrongly attributing it to the bump, it was isolated (re-run 3× standalone, 2× as part of the full suite, all green, both pre- and post-bump) and documented honestly in the plan as sandbox-environment noise, not a finding. Confirms the general discipline of reproducing before concluding, applied to the "is my baseline actually stable" question specifically, not just to the bump's own effect.
- **Phase 4 review earned its keep twice over on a "zero code change" story** — the same pattern story-maint-28's retro named ("Fixing a real audit-completeness gap once a review agent surfaced it"). Both P1 findings (stale version numbers from caret-range drift; a live story-id collision) and the P3 finding (an incomplete import-site inventory, including a real miss inside `harness/` — the plan's own probed blast radius) were genuine, not process theater.

## Change

- **A. A story-id collision with a concurrent, unrelated session was caught by Phase 4 review, not by the Phase 2/R23 pre-check — because the colliding id hadn't been claimed yet when the pre-check ran.** This plan pre-assigned `story-maint-34` to a not-yet-started sibling story (better-sqlite3). Between this story's Phase 2 check and its Phase 4 review (roughly a 20-minute window), a fully independent session opened, completed, and merged PR #263 under the id `story-maint-34`. This is a variant of the gap story-maint-28's retro named (R23's branch-name-only check missing in-flight plan-file content) but harder: there was no PR to check at all yet, because the colliding story didn't exist until mid-flight. No mechanical pre-check closes this gap — the only real mitigation is not writing a *specific* future id into a plan until immediately before that id is claimed (see § Try).
- **B. Caret-range `npm install` resolving newer-than-Dependabot-proposed patch versions is now a reproducible pattern across enough time-gapped stories that plans should stop stating resolved versions as exact.** Three of the seven taken packages resolved to versions newer than Dependabot's own PR body listed, purely because of the gap between when Dependabot generated its proposal and when this session ran `npm install`. Not a defect in this story specifically, but the first draft's table presented the "To" column as a fact about the resolved lockfile rather than as Dependabot's proposal — Phase 4 review correctly distinguished the two.
- **C. The empty-refactor commit's "no source dependency on these packages" claim missed an import site inside `harness/`, the story's own declared probe scope.** `harness/dod-check/lib/gherkin-map.ts` imports `@cucumber/gherkin` and `@cucumber/cucumber-expressions` directly — the plan's first draft asserted these were only "consumed transitively via quickpickle." The probe table already ran `test:harness` and `git diff --stat -- src/ tests/ harness/`, so the harness/ import site was inside the audited surface the whole time; the inventory just wasn't cross-checked against a grep before being asserted. A `grep -rn` for each taken package's name across `src/ tests/ harness/` before writing the Conclusion paragraph — not after Phase 4 finds the gap — is the cheap fix.

## Try

- **When a plan needs to pre-assign a story id to a *not-yet-started* sibling story, treat that id as provisional and re-verify it immediately before drafting the sibling's own plan, not just trust the earlier mention.** This story's own Phase 2 R23 check was clean at the time it ran; the collision only existed by Phase 4. The fix isn't a better pre-check (there's nothing to check yet) — it's not trusting a several-commits-old id assignment once meaningful time has passed. Concrete mechanism used successfully here: re-ran `git ls-tree -r origin/main -- docs/plans/ docs/retrospectives/` fresh, immediately before opening the next sibling story's plan file, rather than reusing the id named in this story's own (now slightly stale) Context section.
- **Grep every taken package's name across `src/ tests/ harness/` as a mechanical step before writing a dependency-bump plan's Conclusion paragraph**, rather than relying on memory of "which packages this repo imports directly." Would have caught Change C's `gherkin-map.ts` gap without needing Phase 4 review to find it. Worth promoting to an explicit line in [docs/templates/maintenance-sub-loop.md](../templates/maintenance-sub-loop.md) if a 4th dependency-bump story reproduces the same class of inventory miss.
