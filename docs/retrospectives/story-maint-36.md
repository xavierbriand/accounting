Phase 4 review pushed this further: verified directly against the lockfile (`hasInstallScript: true` on 12.11.1, absent on 13.0.3) rather than taking the changelog's framing at face value, and the plan now states the security-relevant framing explicitly (fewer install-time code-execution surfaces on a critical-path native dependency) instead of leaving it implicit in an install-speed observation.
- **The one Electron-scoped breaking-change warning in the version range (v12.12.0) was correctly identified as inapplicable rather than triggering a reflexive escalation.** This repo is a Commander CLI with no Electron dependency anywhere in `package.json` — reading the warning's actual scope, not just seeing the word "BREAKING," kept a genuinely-safe bump from being wrongly deferred.
- **Phase 4 review's import-site audit caught a real, if low-materiality, gap a second time in a row** (after story-maint-33's harness/ miss) — this time a type-only import in `src/cli/program.ts` that the plan's first draft didn't enumerate. Neither miss changed the safety verdict, but both are proof the "grep before asserting" discipline story-maint-33's own retro proposed as a Try item is worth actually doing, not just noting.

## Change

- **A. A stale forward-reference to a not-yet-existing story's id reproduced the exact failure class this story itself was renumbered twice to avoid — inside the same plan, within one review cycle.** This story's own Context section, while still being drafted, named the *next* sibling story (chalk) with a specific future id ("story-maint-36") — which happened to be the same id this story ultimately claimed for itself after its own two-collision renumbering. Phase 4 review caught the leftover. The fix isn't a better check — it's simply not writing a specific future id into a plan at all, deferring that to the moment the next story is actually drafted (which is also this story's own § "Maintenance sub-loop" Try-equivalent, applied one story late relative to when it should have been internalized).
- **B. A parallel Phase 4 review agent hit an infrastructure error (monthly spend limit) mid-run, on the first attempt.** Both Phase 4 agents (code-reviewer, sibling-overlap) were launched together; code-reviewer returned partial-but-useful output (it had already found the plan's leftover H1 heading bug — "Story maint-35" instead of "Story maint-36" — before being cut off) and sibling-overlap returned nothing. Retried both cleanly on a second attempt and both completed. The partial output was not discarded — its one confirmed finding was applied immediately, independent of the retry succeeding, rather than waiting to see if the retry would rediscover it.
- **C. Applying a Phase 4 finding introduced a fresh, self-inflicted CI failure that neither review pass caught, because it was written after both passes ran.** The fix for the P1 "incomplete import-site inventory" finding used a `src/infra/db/repositories/*.ts` glob inside the "## Production-code surface (R2)" section. `harness/drift-scan`'s Check B parses that exact section for backtick-quoted `src/`/`tests/`/`harness/` paths ending `.ts`/`.sql` and verifies each exists on disk — it has no glob support, so it flagged the wildcard path as a hard `missing-path` finding, failing CI's `dod-check`/`drift-scan` step outright (`npm run test:harness`'s own drift-scan integration tests, which run the scanner against the live repo rather than a fixture, caught the same thing locally before the push even needed to happen twice). Caught by CI on the first push of the corrected history, not by any review pass — both Phase 4 agents ran *before* this text existed. Fixed by naming the 6 files explicitly instead of globbing.

## Try

- **When a plan needs to gesture at future/sibling work, name it generically ("a further sibling story, id TBD when drafted") rather than pre-committing to a specific number.** This is the second time in one session a pre-assigned future id went stale before it was even used (story-maint-33's plan pre-assigned "story-maint-34" to this story, which then collided and had to renumber twice; this story's own plan repeated the pattern one level further out, pre-assigning "story-maint-36" to the still-undrafted chalk story). Codify as a habit for the remainder of this session and any future maintenance sub-loop: never write a specific `story-maint-N` for work that hasn't started yet.
- **If a Phase 4 review agent is cut short by an infrastructure error, keep and act on any partial findings before retrying** — don't treat a truncated run as pure waste. Worked once already this session (see § Change B); worth stating as a default rather than a one-off recovery choice.
- **Run `npx tsx harness/drift-scan/drift-scan.ts` locally after editing a plan's "## Production-code surface" section, not just after the initial draft.** Any text edit to that section — including a Phase 4 fix — can introduce a glob or otherwise-malformed path Check B chokes on. Cheaper to catch in 2 seconds locally than to discover via a full CI round-trip (see § Change C).
